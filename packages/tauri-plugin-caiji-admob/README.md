# tauri-plugin-caiji-admob

Vendored fork of [tauri-plugin-google-admob](https://github.com/VMASPAD/tauri-plugin-google-admob)
0.1.1 (MIT OR Apache-2.0). Android only — desktop/web get a stub that errors, which is what
`ads.svelte.ts` uses to detect "not on Android" and turn every ad call into a no-op.

## Why we forked

Upstream is effectively abandoned: three commits, all pushed on 2026-02-04, no issues, no
releases since. Two things we need that it will not get:

1. **No UMP/GDPR consent flow.** It has no `user-messaging-platform` dependency at all — only
   `tagForChildDirectedTreatment` / `tagForUnderAgeOfConsent`, which are COPPA flags, not GDPR
   consent. Google requires a certified CMP for EEA/UK/CH users, so without UMP those countries
   have to stay excluded from Play distribution.
2. **Stale ads SDK.** It pins `play-services-ads:24.9.0`, a major version behind.

The alternatives were worse: every other Tauri AdMob plugin that *does* ship UMP
([HMUysal](https://github.com/HMUysal/tauri-plugin-admob-android),
[tontoko](https://github.com/tontoko/tauri-plugin-admob-banner),
[Dreaming-Codes](https://github.com/Dreaming-Codes/tauri-plugin-admob)) drops rewarded and/or app
open ads, both of which we use.

## Why it is not published anywhere

It does not need to be. `tauri android build` generates `gen/android/tauri.settings.gradle` by
resolving each plugin crate's location from cargo metadata and including its `android/` directory
as a gradle subproject — it does not care whether the crate came from a registry, a git ref, or a
path. So a plain `path` dependency is enough:

```toml
# packages/minesweeper-cube/src-tauri/Cargo.toml
tauri-plugin-caiji-admob = { path = "../../tauri-plugin-caiji-admob" }
```

Kotlin edits take effect on the next build, with no publish step. The JS side is a normal
workspace package (`@caiji-games/tauri-plugin-admob-api`, `workspace:*`) that exports TypeScript
directly — the consumer's vite compiles it, same as every other `@caiji-games/*` package.

## The consent flow

`request_consent` runs `requestConsentInfoUpdate` then `loadAndShowConsentFormIfRequired`, and
**must** complete before `initialize()` — the ads SDK has to come up already knowing the consent
state. `ads.svelte.ts` enforces that ordering, and there's a test asserting the call order.

Three things about UMP that are easy to get wrong:

- **It is not an ad on/off switch.** Outside the EEA/UK/CH the SDK reports `notRequired` and no
  form is ever shown. Inside them, a user who *refuses* personalization still gets ads — just
  non-personalized ones — so `canRequestAds` stays true. It only goes false when consent is
  genuinely outstanding.
- **Always branch on `canRequestAds`, never on `status`.** It already accounts for consent stored
  by previous runs.
- **`privacyOptionsRequired` gates the settings entry point.** It's false for most users, so any
  "ad privacy settings" UI must be conditionally rendered or it dead-ends into a form that
  doesn't exist. `AdRewardsSheet.svelte` does this.

A failed `requestConsentInfoUpdate` (usually just no network on a cold start) resolves rather than
rejects, carrying `error` alongside the real `canRequestAds`. Rejecting would lock a
previously-consenting user out of ads because their plane had no wifi.

For testing from a non-EEA country, `requestConsent` takes `debugGeography` (1 = EEA) plus
`testDeviceHashedIds`; the SDK prints the hashed id to logcat on a debug build. `resetConsent`
wipes the stored answer so the form shows again.

## Changes from upstream

- Renamed crate + `links` key to `tauri-plugin-caiji-admob`, npm package to
  `@caiji-games/tauri-plugin-admob-api`, both marked private/`publish = false`.

  **Three names have to agree**, or every command fails at runtime with `not allowed. Plugin not
  found` while the build stays green:

  | Where | Value |
  |---|---|
  | crate name (`Cargo.toml`) | `tauri-plugin-caiji-admob` |
  | ACL namespace — crate name minus the `tauri-plugin-` prefix | `caiji-admob` |
  | `Builder::new()` in `src/lib.rs` | `caiji-admob` |
  | `plugin:…\|cmd` prefixes in `guest-js/index.ts` | `caiji-admob` |
  | consumer's `capabilities/default.json` | `caiji-admob:default` |

  Only the first one is free to change, and only in ways that leave the stripped remainder intact.
  A name like `caiji-tauri-plugin-admob` does *not* work: the prefix isn't at the start, so nothing
  is stripped and the namespace becomes the whole crate name, which then no longer matches
  `Builder::new()`.
- `play-services-ads` 24.9.0 → **25.2.0** (not 25.4.0 — that needs a Kotlin 2.3+ compiler, see the
  toolchain note below); androidx/material versions aligned with the app module;
  library `minSdk` 23 → 24 to match the apps.
- `build.rs` now lists every command, so `permissions/autogenerated/` is genuinely generated.
  Upstream listed only `ping` and hand-wrote the other twelve permissions into a file stamped
  "Automatically generated - DO NOT EDIT".
- **Desktop stub now returns `Err(UnsupportedPlatform)`** instead of upstream's fake
  `Ok { initialized: false }`. A silent success is worse than useless here: `ads.svelte.ts` flips
  `available = true` on any resolved `initialize()`, so the mock-Ok would have turned every later
  ad call into a no-op that still reports success. Note `cargo check` on a dev machine compiles
  this stub and none of the Android code, so a green check says nothing about the real plugin.
  `ping` still succeeds — it never touches the ads SDK, so it stays usable as a wiring probe.
- Dropped the rollup build (`dist-js`) in favour of exporting `guest-js/index.ts` as-is, and
  dropped `.ios_path()` since there is no iOS implementation to point at.
- Deleted upstream's two sample test files. They were Android Studio boilerplate (`2 + 2 == 4`)
  and they did not compile: the template wrote `package com.plugin.google-admob`, and a hyphen is
  not a legal Kotlin package name. Nothing ever caught it because `assembleDebug/Release` skips
  test source sets, so the breakage only shows up if you run a gradle test task. The now-dead
  test dependencies and `testInstrumentationRunner` went with them.
- **Added the UMP consent flow** upstream lacks: `request_consent`, `get_consent_status` and
  `show_privacy_options_form`, plus an explicit `user-messaging-platform:4.0.0` dependency (it
  arrives transitively via play-services-ads, but we call it directly so we declare it directly).

Note on the deprecated age APIs: `setTagForUnderAgeOfConsent` / `setTagForChildDirectedTreatment`
are kept as-is. Their replacement, `setAgeRestrictedTreatment()`, only lands in ads SDK 25.3.0 —
one release past the 25.2.0 the Kotlin 2.1.20 toolchain caps us at. Swap them when the SDK moves.
